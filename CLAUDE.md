# CLAUDE.md — Downwrite

Native macOS Markdown editor (SwiftUI + AppKit/TextKit 1). Goal: Bear-like editing — Markdown syntax hidden unless the caret is inside the pair — as a light-weight default `.md` app. See `README.md` for the user-facing description.

## Layout

| Path | Purpose |
| --- | --- |
| `Sources/DownwriteCore` | **Pure Swift** (Foundation + swift-markdown). No AppKit/SwiftUI. Builds and tests on Linux. |
| `Sources/Downwrite` | macOS-only app target (`#if os(macOS)` in `Package.swift`). |
| `Tests/DownwriteCoreTests` | Core unit tests — run on Linux and macOS. |
| `Tests/DownwriteTests` | macOS integration tests (real `NSTextView`, WKWebView). |
| `Packaging/` | `Info.plist` (template: `__VERSION__`/`__BUILD__`), entitlements, icon artwork + `AppIcon.icon`. |
| `scripts/` | `build-app.sh`, `make-dmg.sh`, `linux-test.sh`, `ci-local.sh`, `generate-icons.py`. |
| `.github/workflows/` | `ci.yml` (Linux core + macOS build/test/e2e), `release.yml` (tag → DMG). |
| `FEATURE-LIST.md` | Table of every user-facing feature with the release it shipped in and that release's date. Keep it current (see *Feature list* under Development workflow). |

## Commands

```bash
scripts/linux-test.sh                  # core tests in the Swift Docker image (works without a Mac)
swift test                             # macOS: everything
swift build && swift run Downwrite     # macOS: debug run
scripts/build-app.sh                   # macOS: dist/Downwrite.app
scripts/ci-local.sh [--shots] [--no-e2e]   # macOS: the whole macOS CI job locally (build, tests, package, real-app e2e) -> artifacts/summary.txt
dist/Downwrite.app/Contents/MacOS/Downwrite --selftest-out=<dir> --selftest-input=<file.md>   # e2e, writes selftest-report.txt
python3 scripts/generate-icons.py      # regenerate icon artwork (needs Pillow)
```

In the cloud (Linux) container there is **no Xcode/macOS**. The app target cannot be compiled there. Workflow that works:
1. Develop and test everything in `DownwriteCore` locally with `scripts/linux-test.sh` (Docker daemon may need `dockerd &`; pull `mirror.gcr.io/library/swift:6.1-noble` if Docker Hub rate-limits).
2. Push the working branch; CI builds/tests the app on `macos-26` (Xcode 26.x, Swift 6.3). Read failures via the Actions logs (`get_job_logs` with a small `tail_lines`; the workflow already prints only error lines).
   No Actions minutes? Run `scripts/ci-local.sh` on a Mac instead (same steps as the macOS job; `--shots` copies screenshots/reports into `docs/` for committing).
3. Put `[shots]` in a commit message to make CI commit fresh screenshots to `docs/screenshots/` (normal push to the same branch — **never** force-push or push other branches from CI or by hand). `git pull --rebase` before your next push.

## Architecture rules

- **All Markdown/editing logic belongs in `DownwriteCore`** so it is unit-testable on Linux. The app target only maps results onto AppKit.
- Offsets are **UTF-16** (`NSRange`) everywhere. cmark reports (line, UTF-8 column); `SourceText.offset(line:column:)` converts. Text in the editor always uses `\n`; `TextCoding` restores CRLF/BOM/encoding on save.
- `MarkdownAnalyzer.analyze` → immutable `MarkdownAnalysis` (spans, markers + reveal ranges, per-line `LineStyle`, links, task boxes, Mermaid blocks, tables). Selection-dependent state (`hidden` markers) is computed on demand by `runs(in:selection:)` / `hiddenMarkerIndices(selection:)`. Reveal rule: selection touches `marker.reveal` inclusive of both boundaries.
- cmark ranges are **wrong for nested emphasis sharing a delimiter run** (`***x***`, `*a **b***`); `MarkdownAnalyzer.effective(_:in:)` shifts children inward. Keep tests in `AnalyzerTests.testUnderscoreEmphasisAndTripleNesting` green.
- Formatting commands (`Formatter`, `ListEditing`, `TableFormatter`) are pure `(text, selection) -> TextEdit?`. The app applies them with `shouldChangeText` → `replaceCharacters` → `didChangeText` so undo works (`EditorTextView.apply`).
- **Hiding syntax** = 0.1 pt clear font on marker characters (`MarkdownStyler`), *not* deleting or glyph-nulling. Whole fence lines / collapsed Mermaid sources use `min/maxLineHeight = 0.1`.
- Editor is **TextKit 1** (`DWLayoutManager`, explicit `NSTextStorage/NSLayoutManager/NSTextContainer`) for predictable custom drawing (code cards, pills, quote bars, rules). Do not touch `textView.textLayoutManager` — that silently flips it to TextKit 2/1 fallback.
- Drawing order in `DWLayoutManager.drawBackground`: custom backgrounds (code cards, pills, quote bars, rules) first, `super` (system selection highlight) last — otherwise a selection inside code is painted over. Inline pills use `pillRects(forCharacterRange:)`: top = baseline − capHeight − gap, bottom = baseline − descender + gap (`pillGapRatio` × font size), *not* the whole line height. `DrawingTests` guard both with pixel checks.
- Fence helpers (`FenceEditing`, Core): typing the third backtick at the start of a line (outside any open fence) replaces it with ```` ```\n\n``` ```` and leaves the caret after the opening fence; Return there steps into the empty body without inserting. `EditorTextView.insertText`/`insertNewline` call it before the normal paths.
- Task checkboxes: a bulleted task's whole `- [ ] ` prefix is one marker (`StyleFlags.taskPrefix`, `TaskBox.prefix`) that reveals only while the caret is *inside* it (the reveal range is the interior, so a caret at the start of the item's text — where you type — never flips the layout; numbered tasks keep their number and raw box). While hidden, `MarkdownStyler` puts a `CheckboxMark` (`.dwCheckbox`) and a `.kern` of `checkboxColumn(size)` on the prefix's first character and `DWLayoutManager` draws the rounded square at that glyph's x (`checkboxRect(forCharacterAt:)`, also the click target); wrapped lines hang at indent + column. A click toggles through `ListEditing.toggleTask(..., keeping: selection)` so the caret never enters the hidden prefix.
- Source view: `EditorCoordinator.sourceMode` (per window, `@State` in `EditorScene`, toolbar `Toggle` left of Format, View ▸ Show Markdown Source ⌘/ via `@FocusedBinding(\.sourceMode)`). `setSourceMode` only changes what is drawn: `restyleAll` → `MarkdownStyler.styleSource` (one plain monospaced run, nothing hidden), `reanalyze` feeds the diagram overlay no blocks, `TableOverlay.gridBlocks` is empty, `collapsed`/`heights` are empty, and `textViewDidChangeSelection`, `reservedHeightsChanged` and task-box clicks return early. The analysis still runs (TOC, word count); text, caret, undo and the Format commands are untouched. `SourceViewTests` guard it.
- Keep on Top: Window ▸ Keep on Top (`WindowCommands`, `@FocusedBinding(\.keepOnTop)`, per-window `@State` in `EditorScene`); `WindowLevelSetter` (a zero-content `NSViewRepresentable` in the scene's `.background`) sets the hosting `NSWindow.level` to `.floating`/`.normal`. `KeepOnTopTests` guard it.
- External changes (backlog item 8): `EditorCoordinator` polls the file's modification date every second (`startWatchingFile`) and on app activation; `checkForExternalChange()` acts only when the date changed, the `NSDocument` is not edited and the decoded file text differs from the editor, and then calls `document.revert(toContentsOf:ofType:)` (so AppKit's own `fileModificationDate` stays in sync and no save-time conflict alert follows). SwiftUI hands the reloaded text to `update(text:settings:)`, which applies it with `TextDiff.replacement` (Core: smallest single replacement, surrogate-safe) + `TextDiff.map` for the caret — scroll position and caret survive — and drops the undo history (stale offsets). With unsaved edits we do nothing; the document system's own alert handles it on save. `TextDiffTests`, `ExternalChangeTests` and e2e step 4b (a real second process, append and atomic rename) guard it.
- Table of contents: `TableOfContents` (Core) flattens `analysis.headings` into `TOCRow`s (depth/parent; skipped levels add no depth) using `HeadingInfo.plainTitle` (the heading as the editor shows it, markers stripped); `MarkdownAnalysis.headingIndex(at:)` maps a caret offset to its section. The sidebar is a SwiftUI `.inspector` in `EditorScene` showing `TOCSidebar`; `TOCModel` (ObservableObject) is fed by `EditorCoordinator` (publishing is deferred one run-loop turn — `reanalyze` runs inside `updateNSView`, where publishing is forbidden) and clicks come back via `TOCModel.onSelect` → `EditorCoordinator.revealHeading(at:)` (caret to end of the heading line, editor first responder, `EditorTextView.scrollToTop`). Visibility is the `showTOC` default (⌃⌘O, toolbar button, View menu). Rows are keyed by heading index, never by offset, so ids stay stable while typing. On macOS 26 the inspector floats over the window: the `NSScrollView` keeps its full-width frame and insets its content (the text view narrows, `scroll.frame` does not) — measure `tv.frame.width` in tests, not the scroll view.
- Folding (display state only): `MarkdownAnalysis.foldRegions` (Core) lists every top-level heading (ATX and setext; a setext heading ends at its real underline, because cmark's range runs over the next line) and every list item with content after its first paragraph — `headerLines` (chevron on the first, ⋯ chip on the last), `hiddenLines`, `anchor` (the UTF-16 start of the header line, a fold's identity) and `hiddenRange`. `FoldState` (Core, `Folding.swift`) is a `Set<Int>` of anchors with the whole state machine: `hiddenLineRanges`, `foldHiding` (decided by the offset's *line*, so a trailing empty line stays a valid caret position), fold/unfold at the caret, all, to level, `revealing`, `visibleOffset`, and `mapped(through:from:to:)`, which moves each anchor through the single replacement `TextDiff` finds (an edit before shifts it, after leaves it, retyping the header keeps it, running into the header or past its last line's content drops it, and a fold is kept only if a region is still anchored there, so it is never handed to different text). The coordinator owns one `FoldState` per window (`EditorFolding.swift`; memory only, no setting): `reanalyze` carries it through every text change by diffing `analyzedText`, opens folds that hide the caret (R15), and passes `PreviewState.setFolds` to the styler; `setFoldState`/`applyFoldState` restyle only the lines whose look changed, hide the grids and cards in hidden lines (`TableOverlay`/`DiagramOverlay.setHiddenLines`, kept apart from "Markdown source showing"), and move a hidden caret to the end of the outermost hiding fold's header. Hidden lines get only `MarkdownStyler.foldedLineHeight` (0.001 pt: the line height alone decides the leftover room, 0.1 pt would leave 100 pt per 1,000 lines) plus a clear 0.1 pt font; `style(lines:)` shares one `runs` computation across separated lines and sets a hidden stretch in one call. Chevron and chip are `.dwFold`/`.dwFoldChip` (`FoldMark`) text attributes drawn by `DWLayoutManager.drawFoldControls`, called from `EditorTextView.drawBackground(in:)` — not from the layout manager's own background pass, whose clip is the text container and cuts off the margin. Caret movement commands run, then `snapCaretOverFolds` moves the end that landed in hidden text in the direction of travel (`isMovingCaret` keeps `selectionChanged` from opening the fold instead); Return, Backspace and Delete (and their variants) at a fold's edge open it first. `FoldingTests`, `FoldTests`, the fold cases in `DrawingTests` and `SelfTestFold.swift` guard it.
- Window chrome: `applyChrome` makes the title bar transparent and paints the window the page colour (so Latte/Mocha have no grey band behind the toolbar). That means nothing may scroll *under* the toolbar — it would show straight through — so `EditorScene` only ignores the leading/trailing/bottom safe area (`.ignoresSafeArea(.container, edges: [.leading, .trailing, .bottom])`); the scroll view starts below the toolbar and its top `contentInsets` stay 0 (`scrollTarget`, `TOCTests` rely on that). e2e step 6i checks the scroll view's top against `window.contentLayoutRect` and that the toolbar strip is pixel-identical with the text at the top and scrolled.
- Settings imported-theme list: `ImportedThemeRow` is a plain `HStack` (name `lineLimit(1)`, *Remove* pinned right). Do **not** use `LabeledContent` there — in a grouped form row it gives the label column only half the width and long names wrap. `ThemeImportOutcome.summary` keeps the status note to `maximumLines` lines. `SettingsTabsTests` render the row (`ImageRenderer`) and the e2e Appearance capture with six imported themes checks where *Remove* sits.
- Light theme background is pure white (`Palette`); cards/rules are neutral greys to match. `AppTests.testLightEditorBackgroundIsPureWhite` and `testLightEditorBackgroundIsWhite` (Core) guard it.
- Inline HTML (backlog: "Render inline HTML in the editor"), two tiers. **Blocks:** `MarkdownAnalyzer.htmlBlock` keeps today's `.html` line kind/span and, for top-level (not quote/list/table-cell) blocks where `HTMLSupport.isRenderable` holds (visible text or an image/rule/etc.; not comments, closing-tag-only, bare wrappers like `<div align="center">`, `<script>`/`<style>`), also records a `RawHTMLBlock`, which `previewBlocks` turns into `PreviewBlock.Kind.html(source:)`. So collapse-while-caret-outside, reserved `paragraphSpacing` and source-view removal are the Mermaid/image machinery. `DiagramView` has a third `Mode.html`: `HTMLSupport.page(body:style:)` (CSP meta *first* in `<head>`: `default-src 'none'; img-src data: https:; style-src 'unsafe-inline'; …`; body wrapped in `#dw-root`) loaded with `loadHTMLString(baseURL: nil)`, page JS off (`allowsContentJavaScript = false`; the app's own `evaluateJavaScript` of `HTMLSupport.heightScript` still works), and a `WKNavigationDelegate` that cancels every navigation but our own main-frame `about:` load. Local `<img>` files are inlined as `data:` URIs by `DiagramOverlay.inlineLocalImages` (`HTMLSupport.imageSources/replacingImageSources`, `ImageLoader.dataURI`, 8 MB cap) so the page never needs file access. HTML reflows: `Entry.renderedWidth` makes `reposition` render again when the column width changes; the entry identity includes `HTMLPageStyle` (palette + font) so theme/font changes re-render; typing is debounced 150 ms. `DiagramOverlay.layoutProblems` and `HTMLCardTests` guard it; e2e step 8 checks the README's centred screenshot rows. **Inline:** `MarkdownAnalyzer.htmlTag` pairs whitelisted tags among the *siblings* of one container (`b strong i em s del strike u ins mark code kbd samp sub sup`, `a` with a non-empty `href`) into a span (+ `.underline/.sub/.sup` flags) and two markers whose reveal range is the whole pair, exactly like `**`; `<a href>` also adds a `LinkSpan`. Anything else (`<br>` — grid cells store line breaks as `<br>` —, `<span>`, strays, never-closed tags) keeps the dim `.html` span.
- Mermaid: `MermaidService` renders SVG in a hidden `WKWebView` (bundled `mermaid.min.js`, `securityLevel: strict`); `DiagramOverlay` owns one click-through `DiagramView` per block and tells the styler how much `paragraphSpacing` to reserve on the block's last line. Source collapses while the caret is outside the block.
- Resources are loaded through `AppResources.url` (app bundle first, SwiftPM `Bundle.module` fallback). `build-app.sh` flattens `Sources/Downwrite/Resources/*` into `Contents/Resources`.
- Settings (`SettingsView.swift`): a `TabView` of three short panes — `AppearancePane` (appearance mode, light/dark theme pickers + `ThemePreview`s, VS Code import and the imported list, which scrolls past four rows), `EditorPane` (typography, spelling), `GeneralPane` (default Markdown app, version, licences) — selected by `Prefs.settingsTab` (`SettingsTab` raw value) so it reopens where it was left. Each pane is `fixedSize(vertical)` at 500 pt wide so the window follows the tab; `SettingsTabsTests` keep every pane under 560 pt tall (the old single pane did not fit on most screens) and the e2e opens ⌘, and checks/captures each tab (the window title is the tab's title).
- Colour themes: `ThemeCatalog` (Core, `Themes.swift`) lists the built-in `ThemeDefinition`s (id, name, appearance, `Palette`): `downwrite-light/dark` (the original `Palette.palette(for:)`, default), `catppuccin-latte/mocha`, `radix-light/dark`; `ThemeCatalog.palette(id:for:)` falls back to Downwrite for unknown ids or an id of the other appearance. The `lightTheme`/`darkTheme` defaults (Settings pickers, `ThemePreview`) travel through `EditorSettings` into `EditorCoordinator.currentPalette`/`refreshPalette`, which picks light or dark by the view's `effectiveAppearance`; `Palette.isDark` (background luminance) replaces comparisons with the Downwrite dark palette. New themes: add a `ThemeDefinition` (keep `ThemeCatalogTests` legibility floors green), and the licence text under `ThirdParty/` + `THIRD-PARTY-NOTICES.md` if the colours come from someone else's palette.
- Imported VS Code themes: `VSCodeTheme.convert` (Core) reads a theme file (`JSONC.sanitize` strips comments/trailing commas; `include` is resolved through a callback; `tokenColors` scopes are matched like TextMate, most specific rule wins) into an `ImportedTheme` (palette + appearance + warnings). Roles missing from the file are derived from page/text, and every foreground is nudged toward the better of white/black (`bestPole`, equal at luminance ≈ 0.18, which is also `Palette.isDark`) until it meets the contrast floors asserted by `VSCodeThemeTests` (including 300 random themes). `StoredTheme` is the on-disk JSON (already converted, `custom-<slug>-<light|dark>` ids); `ThemeLibrary` merges built-ins with imported ones; the app's `ThemeStore` (`@MainActor ObservableObject`, `shared`, folder = Application Support/Downwrite/Themes, `revision` bumped on every reload so open editors repaint through `EditorSettings.themeRevision`) imports, lists and removes them, and `AppearanceResolver.palette(for:lightTheme:darkTheme:)` resolves ids through it. Settings has the *Add VS Code Theme…* button (NSOpenPanel) and a Remove list; removing a chosen theme resets that picker to Downwrite.
- Theme = `NSApp.appearance` override from the `theme` default (`system|light|dark`); palettes live in `Palette` and are picked from the view's `effectiveAppearance`. Dock icon swaps `AppIcon-light/dark.png` by system appearance. The Finder/system icon is `Packaging/AppIcon.icon` (Icon Composer) compiled by `actool` in `build-app.sh`; it uses ONE glyph layer for all appearances (per-appearance glyph overrides were not honoured) and only the background fill changes. Regenerate everything with `scripts/generate-icons.py`.
- Swift language mode is v5 (`swiftLanguageModes: [.v5]`) to avoid strict-concurrency churn in AppKit code.

## Gotchas learned the hard way

- swift-corelibs-foundation (Linux) differs from Darwin: avoid `x as NSString` (use `NSString(string:)`), no Windows-1252 codec (hand-rolled in `TextCoding`), `String(data:encoding:.utf8)` is lossy instead of failing.
- `NSIntersectionRange`, `lineRange(for:)` etc. operate in UTF-16 — never mix with `String.Index`.
- Don't call `NSTextStorage.setAttributes` outside `begin/endEditing`, and ignore selection callbacks while styling (`isStyling` flag in `EditorCoordinator`).
- `textViewDidChangeSelection` fires *before* `textDidChange` when typing; the coordinator guards on `analysis.length == storage.length`.
- Overlays (table grids, Mermaid/image cards) are positioned from the text view's geometry and must be re-positioned on every width change: `EditorTextView.setFrameSize` calls `scheduleReposition()` because a layout-completion callback is *not* guaranteed after a pure width change (sidebar open/close left grids stale and overlapping text). `TableOverlay.layoutProblems()` reports any disagreement between a grid and the text; `TableLayoutTests` and the e2e README scenario assert it is empty.
- Info.plist template tokens are replaced by `build-app.sh`; `AppTests.testInfoPlistClaimsMarkdownFiles` guards the file-association keys.

- A synthesised `mouseDown` that is not on a control falls through to `NSTextView.mouseDown`, which tracks the mouse until the button comes up: post the matching `leftMouseUp` first or the test hangs forever.
- Tests that wait for an animation (the contents sidebar's scroll) or for Mermaid/WebKit rendering need the display awake: with the Mac idle they time out at 25 s and fail. Run `caffeinate -u -t 2` and `caffeinate -d` first.
- The self-test writes the app's real preferences (`theme`, `lightTheme`, `darkTheme`…) and shares them with a running copy. Run it from a copy with its own bundle ID (`PlistBuddy -c "Set :CFBundleIdentifier …"` then `codesign --force --deep -s -`) when you also use the app. Steps that depend on SwiftUI's focused scene (⌘/, Keep on Top, the fold shortcuts) need a normal desktop session.
- `scripts/linux-test.sh` fails under macOS's bash 3.2 (`ENV_ARGS[@]: unbound variable`), and in Docker Desktop's VM a test process randomly wedges (about 1 in 100) — one `swift test` stalls within a few dozen tests. Run the same image with one test per process under a timeout and retry only a timeout.

## Quality bar

- Every Core change ships with unit tests; `scripts/linux-test.sh` must be green before pushing.
- Keep the app **light**: no new dependencies without a strong reason (current: swift-markdown, bundled Mermaid).
- UI changes: add/adjust `StylerTests`/`EditorBehaviourTests` and look at the CI snapshots (`SnapshotTests`, `--selftest` window captures).

## Development workflow (ai-sdlc)

Non-trivial changes go through committed artifacts in `docs/changes/<YYYY-MM-DD>-<slug>/`: `intent.md` → `spec.md` (features only) → `plan.md` → code + tests → `review.md` + PR. Each artifact is committed at its gate, and the next stage starts from the committed file, not from conversation context. Use the `ai-sdlc` skills: `/ai-sdlc:intent`, `/ai-sdlc:spec`, `/ai-sdlc:plan`, `/ai-sdlc:build`, `/ai-sdlc:review`, `/ai-sdlc:status`.

- Never write production code for a change without an approved `plan.md`.
- If the implementation departs from `plan.md`, update the plan in the same commit.
- Never mark your own artifact accepted or approved. Wait for the user.
- Typos, dependency bumps and one-line config changes skip the process.

Commands:

- Test: `scripts/linux-test.sh` (Core, runs anywhere Docker does); `swift test` on macOS for everything
- Lint: `<lint command>` (none configured in this repo yet)

### Feature list

Always update `FEATURE-LIST.md` (repo root) after a new feature has been fully released, meaning it is merged and shipped in a tagged release (`vX.Y.Z`). Append one row at the bottom with the columns Area, Feature, What it does, Release and Released, matching the existing rows.

- Features only. Bug fixes, minor enhancements (small tweaks to an existing feature), refactors, tests, CI and docs do not get a row.
- Release is the tag that first shipped the feature, linked to its GitHub release page. Released is that tag's date, from `git for-each-ref refs/tags/vX.Y.Z --format='%(creatordate:short)'` (the maintainer's local date), not the merge or commit date.
- Never guess a version or a date. If the feature is merged but not tagged yet, tell the user the row is still owed and add it once the tag exists.
